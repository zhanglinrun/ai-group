# `group-buy-market`（团购交易项目）

这是一个围绕团购活动展开的营销交易项目。  
它不只是做商品展示，也不只是做订单记录，而是在管理一场团购交易从开始到结束的完整过程：活动展示、优惠试算、锁单占位、支付结算、退款回补、通知补偿。

如果你正在学 `Java`（编程语言）业务项目，这个仓库比较适合拿来练下面几件事：

- 看懂一个真实一点的团购交易主线。
- 理解 `DDD`（领域驱动设计）在工程里的基本落地方式。
- 理解规则链、策略、仓储、消息、定时补偿这些写法为什么会出现在业务系统里。
- 在已有项目上做小改动，再顺着日志、数据库和测试验证结果。

## 项目到底在做什么

可以先把这个项目理解成一句话：

它是在管理“用户参加团购活动”这件事的全过程。

这条主线大致是这样的：

1. 用户进入活动页，系统查询活动和商品信息。
2. 系统先做一次试算，算出原价、优惠和最终支付价。
3. 用户发起锁单，系统先占住这次交易资格和拼团名额。
4. 用户支付成功后，系统进行结算，更新订单和团状态。
5. 如果超时、失败，或者后续出现逆向场景，系统进入退款、回补、通知和补偿流程。

所以它不是一个“查活动表、插订单表、改状态表”就结束的项目。  
它更像一条完整的交易链路。

## 这个项目里主要有哪些内容

从业务上看，项目里最核心的是下面几块：

- 活动试算：根据商品、活动、人群标签、渠道信息算出可见性、可参与性和优惠价格。
- 锁单占位：在支付前先校验活动是否可用、用户是否超限、团队名额是否还能占。
- 支付结算：支付成功后推进订单状态和拼团状态变化，必要时生成回调任务。
- 退款回补：处理未支付超时、已支付未成团、已支付已成团后的逆向流程。
- 通知补偿：业务执行完以后，不是所有动作都同步完成，后面还会有回调、重试和补偿。
- 动态配置：支持通过配置动态调整开关、切量、限流这类运行时行为。

从学习上看，这个项目适合用来理解下面这些内容：

- `Maven`（构建工具）多模块工程怎么拆。
- `trigger`（入口层）、`domain`（领域层）、`infrastructure`（基础设施层）怎么分工。
- 规则链、策略模式、仓储接口这些写法在真实业务里的作用。
- `Redis`（缓存）占库存、`RabbitMQ`（消息队列）通知、定时任务补偿怎么和主流程配合。

## 业务主线

先不要急着看代码，先把这条业务主线装进脑子里：

`进入活动页`（用户查看活动）
-> `试算`（确认价格和资格）
-> `锁单`（先占住资格和名额）
-> `支付成功`（外部支付完成）
-> `结算`（更新订单和拼团状态）
-> `退款或补偿`（失败、超时或逆向场景处理）

这里最容易忽略，但又最重要的一步，是 `锁单`（支付前占位）。

因为团购不是“谁付款成功谁就算数”这么简单。  
如果不先锁单，并发下就很容易出现重复参团、名额超卖、支付后才发现团已满、后续大量退款这些问题。

## 工程结构

这个仓库是一个 `Maven`（构建工具）多模块工程。  
最核心的 6 个模块如下：

- `group-buy-market-app`（启动配置模块）
  负责启动应用、加载配置、注册线程池、日志、`MyBatis`（持久层框架）等运行时能力。

- `group-buy-market-trigger`（入口层模块）
  负责接住系统外部的触发动作，包括 `HTTP`（接口请求）、定时任务、消息监听。

- `group-buy-market-domain`（领域层模块）
  负责核心业务规则。这里按业务又拆成了 `activity`（活动域）、`trade`（交易域）、`tag`（标签域）。

- `group-buy-market-infrastructure`（基础设施层模块）
  负责把领域层需要的能力真正落到技术实现上，例如数据库、`Redis`（缓存）、消息、外部回调。

- `group-buy-market-api`（接口定义模块）
  放服务接口、`DTO`（数据传输对象）、统一返回对象这些对外约定。

- `group-buy-market-types`（公共类型模块）
  放枚举、异常、常量、事件基类这些多个模块都会用到的公共内容。

你可以先把模块关系理解成下面这样：

- `app`（启动配置）负责把系统装起来。
- `trigger`（入口层）负责接请求、接任务、接消息。
- `domain`（领域层）负责处理真正的团购业务。
- `infrastructure`（基础设施层）负责查库、写库、占缓存、发消息、调外部服务。
- `api`（接口定义）负责约定输入输出。
- `types`（公共类型）负责提供通用表达。

## 系统入口

这个项目的入口不只有接口请求。  
从代码结构看，它至少有 3 类入口。

### 1. `HTTP`（接口请求）入口

主要接口都在 `group-buy-market-trigger`（入口层模块）里：

| 接口路径 | 作用 |
| --- | --- |
| `/api/v1/gbm/index/query_group_buy_market_config` | 查询活动页需要的营销配置，同时做试算。 |
| `/api/v1/gbm/trade/lock_market_pay_order` | 发起锁单，先占住这次团购交易资格。 |
| `/api/v1/gbm/trade/settlement_market_pay_order` | 支付成功后做结算。 |
| `/api/v1/gbm/trade/refund_market_pay_order` | 发起退单或逆向处理。 |
| `/api/v1/gbm/dcc/update_config` | 更新动态配置，例如开关、切量、限流参数。 |

### 2. 定时任务入口

定时任务也放在 `trigger`（入口层）里，当前比较关键的有两个：

- `GroupBuyNotifyJob`（拼团回调通知任务）
  定时扫描待通知任务，把该回调的结果继续往外推。

- `TimeoutRefundJob`（超时未支付退单任务）
  扫描超时未支付订单，触发退单和回补动作。

### 3. 消息监听入口

项目里还有 `RabbitMQ`（消息队列）监听器：

- `TeamSuccessTopicListener`（组队成功消息监听）
  负责接收拼团完结相关消息。

- `RefundSuccessTopicListener`（退单成功消息监听）
  负责在退单成功后恢复锁单量，走最终一致性处理。

## 领域划分

`group-buy-market-domain`（领域层模块）里，最重要的是 3 个业务域：

### `activity`（活动域）

这里主要负责活动页查询和优惠试算。  
你会看到根节点、标签节点、开关节点、市场节点、结束节点这类编排方式，用来把试算流程拆开。

这一块主要在回答：

- 用户能不能看到这个活动。
- 用户能不能参加这个活动。
- 当前商品应该按什么优惠规则计算价格。

### `trade`（交易域）

这里是交易主线的核心：

- 锁单
- 结算
- 退款
- 通知任务
- 锁单量回补

如果你只想先看一条最重要的业务链，优先看这里。

### `tag`（标签域）

这里主要处理人群标签相关能力。  
项目里的活动可见性、可参与性，不只是看活动本身，也会看用户是不是落在人群范围里。

## 核心业务能力

下面这几块，是 README 最想帮你先建立的业务感觉。

### 1. 首页查询不只是查商品

活动页查询并不是简单返回商品价格。  
它还会顺带做营销试算，判断：

- 当前活动有没有生效。
- 用户是不是在人群范围内。
- 优惠规则该怎么计算。
- 当前有哪些正在进行中的拼团队伍可以加入。

所以首页接口背后其实已经带着业务判断。

### 2. 锁单不是下单完成，而是先占位

锁单阶段会先做一轮关键判断，例如：

- 活动是否生效、是否还在有效期。
- 用户在这个活动上是否超出参与次数。
- 当前拼团队伍是否还有可占用名额。
- 外部交易单号是否已经存在，避免重复下单。

锁单做完以后，系统会先把这笔交易和团状态占住，但这还不是最终成交。

### 3. 结算是在推动团状态变化

支付成功后，系统做的不是单纯把订单改成“已支付”。  
它还要继续判断：

- 这笔订单属于哪个团队。
- 当前团队已经完成了多少支付。
- 现在是不是刚好达到成团目标。
- 是否需要生成回调任务通知外部系统。

所以结算本质上是在推动“拼团是否成功”这件事。

### 4. 退款不只有一种

真实业务里，退款不是一个 `if else`（条件分支）就能讲完。

这个项目里至少会遇到这些场景：

- 下单后一直没支付，超时退单。
- 已支付，但团没成，需要逆向处理。
- 已支付，团已成，但后面又发生退款。

不同场景下，需要恢复的数据和触发的动作都不一样，所以项目里用了不同退款策略来处理。

### 5. 业务结束以后，后面可能还有一串尾巴

这是很多新手第一次看业务系统时最容易忽略的地方。

主流程执行完，不代表整个业务就真的结束了。  
后面可能还有：

- 回调通知外部系统。
- 本地消息补发。
- 定时任务重试。
- `MQ`（消息队列）消费失败后的再次投递。
- 锁单量恢复和库存回补。

这也是为什么项目里会有 `notify_task`（通知任务表）和多个任务、监听器。

## 数据库里最核心的几张表

如果你准备结合数据库一起看代码，建议先认识下面这些表：

- `group_buy_activity`（拼团活动表）
  存活动本身的时间、目标人数、限购次数、标签范围、状态等信息。

- `group_buy_discount`（优惠规则表）
  存优惠方式和优惠表达式，例如直减、满减、`N`（固定金额）元购。

- `group_buy_order`（拼团队伍表）
  存某个团队当前的拼团进度、目标人数、锁单数量、完成数量和有效期。

- `group_buy_order_list`（交易订单明细表）
  存某个用户在某个团里的实际交易记录，包括外部交易单号、价格、状态等。

- `notify_task`（通知任务表）
  存后续需要回调或重试的任务。

- `crowd_tags`（人群标签表）、`crowd_tags_detail`（人群标签明细表）
  存标签本身和用户与标签的对应关系。

代码如果只看 `Java`（编程语言）类，不结合这些表，很容易觉得很多字段不知道为什么存在。  
但和表结构一起看，很多状态就会清楚很多。

## 本地启动建议步骤

下面是一条比较稳的本地启动顺序。

### 1. 先启动中间件

可以参考 `docs/dev-ops/docker-compose-environment.yml`（本地中间件编排文件）准备：

- `MySQL`（数据库）
- `Redis`（缓存）
- `RabbitMQ`（消息队列）

如果你直接用 `Docker`（容器工具）启动，可以执行：

- `docker-compose -f docs/dev-ops/docker-compose-environment.yml up -d`（启动本地依赖中间件）

### 2. 初始化数据库

优先选择一套完整脚本导入，不要把不同版本脚本混着用。  
一般可以先用：

- `docs/tag/v3.0/mysql/sql/group_buy_market.sql`（数据库初始化脚本）

### 3. 修改开发环境配置

启动前先检查 `group-buy-market-app/src/main/resources/application-dev.yml`（开发环境配置文件），至少确认下面几类配置能连通你的本地环境：

- `spring.datasource`（数据库配置）
- `spring.rabbitmq`（消息队列配置）
- `redis.sdk.config`（缓存配置）
- `xfg.wrench.config.register`（动态配置注册配置）

这里建议特别注意一点：

`RabbitMQ`（消息队列）的业务连接端口和管理后台端口不是一回事，启动前最好核对一下你填的是实际可连接的业务端口。

### 4. 构建项目

在仓库根目录执行：

- `mvn clean install -DskipTests`（跳过测试先完成构建）

### 5. 启动应用

你可以选下面任意一种方式：

- 在 `IDEA`（开发工具）里直接运行 `cn.bugstack.Application`（主启动类）
- 执行 `mvn -pl group-buy-market-app -am spring-boot:run`（从根工程启动应用）

默认开发环境里，服务端口是 `8091`（应用访问端口）。
