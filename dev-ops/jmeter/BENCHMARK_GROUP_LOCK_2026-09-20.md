## 修改与观察

1. Redis 预占原先 `incr + 1` 多计一席，拒绝时还会 `setAtomicLong` 覆盖并发递增。现用单次 Lua 原子比较/递增，团主占第一席，拒绝不改计数，设置计数键过期；MySQL `updateAddLockCount` 增加 `activity_id` 条件，仍是人数权威。
2. 初始开发配置 Tomcat `max-connections=20`。2000 个请求在 234 ms 内开始，864 笔在 30 s 读取超时；仅改为 2500 后一轮 2000 请求超时为 0。随后新团成功路径在 20 个工作线程处进入吞吐平台，临时提升到 40 后 100 客户端档约 660→784 TPS、P99 230→207 ms；开发配置最终为 `threads.max=40`、`max-connections=2500`，DB 池仍为 25。
3. 成团结算对已 COMPLETE 的成员做幂等回放，包括 COMPLETE、COMPLETE_FAIL 团和已过期的 PROGRESS 团；未结算明细在终态团仍拒绝。XXL-JOB 初始化 SQL 中损坏的列名已修复，以便隔离业务栈启动。
4. 新增固定团一次性尖峰计划、每次运行独立外部单号前缀、业务码分组及只读 SQL。当时报告要求全部请求、至少一笔占位、无异常业务码/传输错误、样本起始跨度不超过 5 s；满团拒绝不算成功锁单。这是历史判定口径，不等于现在的自动 DB 正确性门禁。

最终团 `15e89d1afadf4d848c2af8113e1c5904` 的 `verify_group_lock_fixed_team.sql` 结果：`target=3`、`lock_count=3`、有效明细=3、当前批次明细=2、`counters_consistent=1`；重复业务键、跨活动/团/商品/来源渠道和通知 UUID 异常查询均无行。错活动 DB CAS 的可回滚探针更新 0 行，匹配活动更新 1 行，回滚后人数不变。

以上历史数值保留原始口径，旧 JTL 缺少 `outTradeNo` 样本列，不能用新门禁反向宣称这些轮次自动通过；当时的 SQL 对账为人工检查。

### 严格门禁复测

新脚本要求预检剩余名额与成功锁位数**精确相等**，JTL 保存每笔 `outTradeNo`，并自动保存同一 MySQL 只读事务的前后快照。`20260920051231929` 的 20 请求冒烟通过：预期 2 席、成功 2、容量拒绝 18、DB 后检无差异。

`20260920051440612` 的 2000 请求独立团尖峰：请求起始跨度 527 ms，成功锁位 2、容量拒绝 1998、HTTP/断言错误 0；成功锁单平均 290 ms、P99 401 ms；全体响应 P99 10.393 s 主要是满团拒绝。前快照 `target/lock/detail=3/1/1`，后快照为 `3/3/3`，本批次新增明细 2，通知任务始终 0。成功 JTL 外部单号集合与新增 DB 明细集合相同，`verification.json` 为 `passed=true`。这证明该隔离团在本次尖峰中零超卖，不证明 2000 TPS 或生产容量。

## 故障注入

只停止 `ai-group-bench-redis-1`，对有空位的团 `584dc297898c427999a9fd57756b3471` 发 1 笔请求（`20260920031448430`）：返回业务码 `0001`，本次故障测试按预期失败，DB 团人数/明细仍为 1/1。恢复该 Redis 后 Group 健康项 UP，同团新请求 `20260920031539238` 成功，DB 为 2/2。本测试验证 Redis 不可用时无错误落库与恢复后的可用性，不覆盖进程在 Redis 预占后、DB 提交前崩溃的恢复窗口。

## 边界与复现

- 隔离栈启动命令与新卷说明见 `dev-ops/jmeter/README.md`；必须同时使用 `dev-ops/jmeter/bench-compose.override.yml` 和项目名 `ai-group-bench`，否则完整 Compose 会复用旧项目的网络名。现有同名测试卷会保留先前压测数据。
- 固定团复测仅对本机 `ai-group-bench` 隔离栈进行。先在 `ai-group-bench-mysql-1` 的 `group_buy_market.group_buy_order` 中只读确认现有团队的 `status=0`、`valid_end_time>NOW()`、`activity_id`、`source/channel=s01/c01` 与 `target_count-lock_count`；选无并行结算/退款/锁单流量的团队，使用 `sc_sku_activity` 核对商品。绝不修改数据库创建空位。用 `pwsh -File dev-ops/jmeter/run-group-lock-fixed-team.ps1 -TeamId <team> -ActivityId 100201 -GoodsId 9890002 -ExpectedFreeSlots <精确空位数> -Threads 2000`；服务匹配的 `AI_GROUP_INTERNAL_TOKEN` 和 `AI_GROUP_IDENTITY_SIGNING_SECRET` 只放进进程环境。脚本自动在发压前/后执行只读快照，分别保存 `db-pre.json`、`db-post.json`，并在 `verification.json` 对照成功 JTL 样本的 outTradeNo 集合；同时核对 `summary.json`、runner 退出码。DB 不可用或有任何不一致即失败，前置校验失败不发送流量。需按硬件条件先做小并发验证，2000 尖峰须等独立环境就绪。
- 新团计划：`pwsh -File dev-ops/jmeter/run-group-lock.ps1 -Threads 20 -Duration 30`。本地工具测试（无需服务）：`python -m unittest discover -s dev-ops/jmeter/plans -p test_group_lock_fixed_team.py`。
- 不将拒绝响应 TPS 作为成功锁单吞吐；不根据单机 30 s 档乘实例数估算容量。仍需异机发压、固定速率 20 QPS 预热、每档数分钟稳态、CPU/GC/DB 锁等待与连接池指标、支付/成团/退款端到端及故障恢复矩阵。
- Redis 预占与 DB 事务之间进程崩溃仍可能临时损失可用席位；恢复计数键的生命周期/对账、活动参数变更后的老团预过滤尚未由本次故障测试覆盖。大团通知载荷列已改为 MEDIUMTEXT，旧卷需执行 `group-service/docs/dev-ops/mysql/sql/3-05-notify-task-payload.sql`；隔离 MySQL 已验证 80,011 字节载荷可写入并回滚，但大目标人数的端到端成团仍待测试。
- XXL-JOB 初始化 SQL 可在全新卷上完成，但仍非可重复执行的迁移：对已有 XXL 数据库手动重放会遇到表/主键冲突，新增调度任务须走独立迁移或显式核验。
